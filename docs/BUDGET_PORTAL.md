# ORG-001A Budget Portal

ORG-001A adds narrowly scoped, read-only budget sharing without creating a
general organization role system. It does not make a leader an owner, editor,
bookkeeper, or approver.

## Owner workflow

1. Open **Budgets → Budget Access** (or visit **Settings → Budget Access**).
2. Enter the leader's email and optional display name.
3. Select one or more existing budget IDs. A parent and child budget may both
   be assigned, but their cards overlap and must not be added together.
4. Use **Preview permitted summary**. The preview is generated by the same
   finalized-financial and nested-category calculation used by the owner Budget
   page.
5. Select **Grant access**. Update or revoke the assignment from the same page.
6. Set **Reviewed through** only after activity for the ledger has been checked
   through that date. This date is ledger-wide, not account- or budget-specific.

Deleted budgets disappear from the next portal refresh and are reported as an
unavailable assignment. A budget for a new year has a new stable ID and must be
assigned explicitly. There is no automatic access inheritance.
The current Budget record has no archive state. If archiving is added later, an
archived budget must be treated as unavailable until the owner explicitly
reactivates and reassigns it.

## Leader workflow

1. On `/signin`, select **View a budget with a code**.
2. Enter the exact invited email address.
3. Paste or type the six-digit code from the email. The input supports mobile
   `one-time-code` autofill.
4. View the assigned cards at `/budgets/view`. Use **Refresh** for an immediate
   calculation; an active page also refreshes every 60 seconds without
   overlapping requests.
5. Select **Sign out** when finished. The viewer session uses browser-session
   persistence and ends when that browser session closes.

Requests always return a neutral message, whether or not an invitation exists.
Codes expire after ten minutes, can be used once, lock after five failed
attempts, and are replaced by a resend. A 60-second resend cooldown and shared
Firestore rate limits by keyed email and request source apply across App Hosting
instances.

## Identity and permission design

The server creates a Firebase custom token only after an atomic PIN redemption.
The token uses a synthetic UID (`budget_viewer_…`) and the custom claim
`ledgerlyRole=budget_viewer`; it never reuses the owner's Firebase UID or email
identity. The browser signs it into a separately named Firebase app/Auth
instance with session-only persistence. Therefore a viewer email may equal an
existing owner email without replacing or elevating that owner session.

Portal endpoints verify Firebase Auth and App Check, require the viewer claim,
then reread the current server-only mapping and grants on every request. Owner
API authentication rejects the viewer claim. Firestore rules also reject a
viewer claim below every `/users/{uid}` path, even if a forged token/path uses a
matching UID. Grant, challenge, verifier, viewer mapping, audit, and local-email
collections are Admin-only. Revocation is effective on the next manual or
periodic refresh.

Only calculated fields are returned: budget identity/name/period, budgeted and
recorded cents, remaining cents, percentage, over-budget status, authorized
category summary, and freshness labels. Raw transactions, account identifiers,
receipts, donors, payroll detail, and unrelated ledger totals are never in the
portal response. Responses use `Cache-Control: private, no-store`, and sign-out
clears the displayed response before clearing the viewer session.

| Capability | Owner session | Viewer session | Direct Firestore viewer |
|---|---:|---:|---:|
| Manage grants and reviewed-through date | Yes | No | No |
| Read owner transactions or account records | Yes | No | No |
| Read assigned calculated budget summaries | Preview/API | Portal API only | No |
| Edit budgets or financial records | Yes | No | No |
| Use regular owner APIs | Yes | No | N/A |

The implementation follows Firebase's official guidance for [custom-token
authentication](https://firebase.google.com/docs/auth/admin/create-custom-tokens),
[web Auth persistence](https://firebase.google.com/docs/auth/web/auth-state-persistence),
and [App Check on a custom backend](https://firebase.google.com/docs/app-check/custom-resource-backend).

## Data freshness

The portal deliberately shows three independent facts:

- **Summary updated**: when the server calculated the displayed values.
- **Bank activity synced**: the latest successful active Plaid Item sync, with
  `unknown`, `current`, `stale`, `partial`, or `failed` coverage. Account names
  and identifiers are omitted.
- **Reviewed through**: an owner-maintained, ledger-wide statement of manual
  completeness. It remains `Not set` until an owner supplies it.

A current calculation does not imply that bank activity is complete. A current
bank sync does not imply that the owner reviewed or categorized everything.

## Local isolated setup

The established isolated command now supplies a test-only email transport and a
non-production PIN pepper:

```bash
npm run test:e2e:isolated
```

It starts Auth and Firestore emulators for the fail-closed
`ledgerly-release-demo` project, seeds synthetic owners/budgets/transactions,
captures emails in the Admin-only `budgetPortalTestEmails` collection, starts
Next.js, and runs Chromium. It refuses production mode, a different project ID,
or different emulator hosts. Never use `BUDGET_PORTAL_EMAIL_PROVIDER=test` in
production.

For ordinary local development, add these uncommitted values to `.env.local`:

```dotenv
BUDGET_PORTAL_EMAIL_PROVIDER=test
BUDGET_PORTAL_PIN_PEPPER=<at-least-32-random-characters>
```

## Production prerequisites

### 1. Configure Resend

1. In Resend, open **Domains → Add Domain**, add `ledgerly.business`, publish
   the supplied SPF/DKIM DNS records, and wait for **Verified**.
2. Open **API Keys → Create API Key**. Choose **Sending access** and restrict the
   key to the verified domain where available.
3. Keep the key visible only long enough to enter it into Secret Manager. The
   checked-in sender is `Ledgerly Pro <budgets@ledgerly.business>`; create that
   mailbox/alias and change `BUDGET_PORTAL_EMAIL_FROM` in App Hosting if a
   different verified sender is used.
4. Send an external test to two real providers during the pilot. Local capture
   proves template and flow behavior, not production deliverability.

### 2. Create and grant App Hosting secrets

From an authenticated Firebase CLI, use interactive prompts so values do not
appear in shell history:

```bash
firebase apphosting:secrets:set BUDGET_PORTAL_PIN_PEPPER --project ledgerly-pro --location us-central1
firebase apphosting:secrets:set RESEND_API_KEY --project ledgerly-pro --location us-central1
firebase apphosting:secrets:grantaccess BUDGET_PORTAL_PIN_PEPPER,RESEND_API_KEY --backend studio --project ledgerly-pro --location us-central1
```

Generate the pepper with a cryptographically secure password generator or
`openssl rand -base64 48`, paste it into the first prompt, and do not reuse it as
a password. Rotating it immediately invalidates all outstanding PINs but does
not revoke active viewer grants. Firebase documents both code-first secret
references and backend grants in [App Hosting
configuration](https://firebase.google.com/docs/app-hosting/configure#store-and-access-secret-parameters).

The same work can be done in **Firebase Console → App Hosting → studio →
Settings → Environment**, but the two secret resources must exist in Secret
Manager and the App Hosting service identity must have Secret Manager Secret
Accessor. Console values override `apphosting.yaml`.

### 3. Allow Firebase custom-token signing

App Hosting uses Application Default Credentials. In Google Cloud Console:

1. Open **APIs & Services → Library**, enable **IAM Service Account Credentials
   API** if it is disabled.
2. Open **Firebase App Hosting → studio → Settings** and record the backend
   runtime service-account email.
3. Open **IAM & Admin → Service Accounts**, select that runtime service account,
   open **Permissions**, and grant that same runtime principal **Service Account
   Token Creator** on the signing service account. The required permission is
   `iam.serviceAccounts.signBlob`.
4. Validate one PIN sign-in in the pilot. A 503 containing no secret but a
   server-side `signBlob`/custom-token error means this permission is incomplete.

Do not download or deploy a long-lived service-account key. See Firebase's
[custom-token service-account guidance](https://firebase.google.com/docs/auth/admin/create-custom-tokens#letting_the_admin_sdk_discover_a_service_account).

### 4. Authentication and App Check

1. Firebase Authentication must already be enabled for the existing web app;
   no new password provider is needed. Custom tokens create isolated viewer
   identities in the same Firebase Auth tenant.
2. Keep `FIREBASE_APP_CHECK_MODE=monitor` for the first portal pilot. Confirm
   PIN request, verify, grant, and summary routes produce valid App Check traffic
   from every supported domain.
3. App Check custom-route enforcement is an application rollout decision.
   Firestore and Authentication enforcement are separate switches in **Firebase
   Console → App Check → APIs**. Do not enable any one of them merely because
   another has clean metrics.
4. Development debug tokens belong only in isolated environments and never in
   source control.

### 5. Firestore configuration

No composite index is required by ORG-001A. `firestore.indexes.json` adds TTL
policies for expired challenges, PIN state, and local test mail. The repository
rules deny all direct client access to portal-control collections and deny
viewer claims from owner data.

Production currently has the older broad per-owner rules baseline; the hardened
repository rules remain prepared but unpublished. The portal still cannot read
another user's ledger under the old UID boundary, and all portal data paths are
Admin-only, but publish the hardened rules in the separate staged step below to
remove viewer access even to an empty synthetic UID subtree.

## Deployment order

1. Review and commit the exact diff. CI runs install, lint, typecheck, unit
   tests, rules tests, and build; rerun the isolated browser flow.
2. Verify/enable backups or PITR before changing production rules, per the
   release checklist.
3. Verify the Resend domain/sender. Create the two secrets, grant App Hosting
   access, enable custom-token signing, and keep App Check in monitor mode.
4. Roll out **application code first**. Do not send or redeem a real invitation
   yet. Smoke test owner sign-in, Budget Access loading, and the neutral response
   to an uninvited test email. A viewer token must not be issued while the older
   rules baseline is still active.
5. Observe errors and App Check telemetry. Roll back the app if PIN issuance,
   owner authentication, or normal financial workflows regress.
6. Let older clients drain, then publish Firestore rules and indexes as a
   separate action:

   ```bash
   firebase deploy --only firestore:rules,firestore:indexes --project ledgerly-pro
   ```

7. Repeat owner and viewer smoke tests. Restore the previously verified rules
   if a legitimate owner workflow receives `permission-denied`.
8. Only after the hardened rules pass the production smoke test, invite exactly
   two pilot leaders. Keep App Check enforcement off until valid
   traffic from their real browsers is visible and unexplained invalid/outdated
   traffic is resolved. Enforce custom routes, Firestore, and Authentication
   only as separately authorized, reversible decisions.

Application rollback and Firestore-rule rollback are independent as long as the
new app remains compatible with the verified baseline. Never loosen owner
authorization to solve an App Check problem.

## Two-leader pilot checklist

- [ ] Leader A receives one budget; Leader B receives a different budget; one
  additional budget is shared by both.
- [ ] One invited address is also an existing Ledgerly owner email. Owner and
  viewer sessions remain separate, including an already-open owner tab.
- [ ] Both external mailboxes receive the template promptly; spam placement and
  sender alignment are checked.
- [ ] Invalid, expired, reused, and superseded codes fail without revealing
  whether another email is invited.
- [ ] Each leader sees only assigned cards and no raw transaction/account data.
- [ ] A split expense and linked refund match the owner Budget page to the cent.
- [ ] A new finalized expense appears after Refresh; pending/removed/transfers do
  not affect recorded spending.
- [ ] Changing assignments updates the next refresh; revocation clears the open
  portal on its next request.
- [ ] Owner APIs return 401 to a viewer token; direct Firestore owner/grant reads
  are denied.
- [ ] Mobile one-time-code autofill, paste, keyboard navigation, visible focus,
  Refresh, and Sign out work on iOS/Android pilot devices.
- [ ] Logs contain challenge IDs/status only—never PINs, credentials, donor data,
  or financial records.
